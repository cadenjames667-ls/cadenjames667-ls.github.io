What It Is

Every page on this site — this one included — is a single static HTML file with its styles and scripts inline. There's no React, no npm install, no build step: what's in the git repo is exactly what GitHub Pages serves. Pushing to main is the entire deploy pipeline.

Underneath that simplicity are three independent Firebase projects — one each for Pantry, Furnder, and the visit-log behind /admin/ — plus a from-scratch design system (color tokens, type scale, card and diagram styles) reused across every project write-up page rather than pulled from a component library.

Three separate Firebase projects, on purpose — Pantry, Furnder, and the visit-log each get their own, so a misconfigured or intentionally open rule set in one (Pantry's are wide open, by design, for a test project) has no way to touch the others' data.

Key Engineering Decisions
  • Zero build step. Every file is deploy-ready as written. No bundler, no node_modules, no CI step beyond "push to main" — GitHub Pages serves the repo directly.
  • A design system without a component library. The same CSS custom properties and component patterns (cards, tag pills, diagram panels) are repeated at the top of each page rather than centralized in a shared stylesheet. That's a real tradeoff — some duplication — made deliberately to keep every page a fully self-contained file with no build-time dependency between them.
  • Write-ups separate from live apps. Pantry and Furnder's homepage cards link to a write-up page first (architecture, data model, decisions), with an explicit "Try It" through to the actual running app — so context comes before the demo, not after.
  • The admin dashboard is really auth-gated, not just hidden. /admin/ requires a real Firebase Auth sign-in, and Firestore's security rules restrict reads to one specific account UID server-side — the same "enforcement lives in one place, enforced by the server" principle behind Meridian Trust, applied here too.
  • Known weaknesses are documented, not hidden. Pantry's open Firestore rules are called out in plain language on its own write-up page, in this repo's README, and on the live app itself. A portfolio that names its own project's rough edges reads as more credible than one that hides them.
  • There's a little fun in here too. Somewhere on the homepage is a hidden, fully interactive easter egg. No spoilers — if you're the type to click around, you'll find it.
