9// —— what it is ——
10Every page on this site — this one included — is a single static HTML file with its styles and scripts inline. There's no React, no npm install, no build step: what's in the git repo is exactly what GitHub Pages serves. Pushing to main is the entire deploy pipeline.
11Underneath that simplicity are 3 independent Firebase projects — one each for Pantry, Furnder, and the visit-log behind /admin/ — plus a from-scratch design system reused across every write-up page rather than pulled from a component library.

15Three separate Firebase projects, on purpose — Pantry, Furnder, and the visit-log each get their own, so a misconfigured or intentionally open rule set in one (Pantry's are wide open, by design, for a test project) has no way to touch the others' data.
18// —— key engineering decisions ——
19zeroBuildStep: Every file is deploy-ready as written. No bundler, no node_modules, no CI step beyond "push to main" — GitHub Pages serves the repo directly.
20designSystemWithoutLibrary: The same CSS custom properties and component patterns are repeated at the top of each page rather than centralized. That's a real tradeoff — some duplication — made deliberately to keep every page a fully self-contained file with no build-time dependency between them.
21writeUpsBeforeApps: Pantry and Furnder's homepage cards link to a write-up page first (architecture, data model, decisions), with an explicit "Try It" through to the running app — context before the demo, not after.
22adminIsReallyGated: /admin/ requires a real Firebase Auth sign-in, and Firestore's rules restrict reads to one account UID server-side — the same "enforced by the server" principle behind Meridian Trust, applied here too.
23weaknessesDocumented: Pantry's open Firestore rules are called out in plain language on its own write-up page, in the README, and on the live app itself. Naming a project's rough edges reads as more credible than hiding them.
