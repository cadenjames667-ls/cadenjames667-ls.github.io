Meridian Trust

A role-based access control system with compliance-grade audit logging, modeled on enterprise and banking identity patterns. A working demo of how enterprise and banking software actually governs who can view accounts, edit them, approve transactions, and review the compliance trail.

What It Is

Meridian Trust is a fictional bank's internal access-control system, built to mirror the real question every access-control system exists to answer:

"Is this specific person allowed to do this specific thing, right now?"

That question splits into three deliberately separate layers, and keeping them separate — rather than tangled into one set of conditionals — is the core engineering idea the project demonstrates:

  1. Authentication — Who are you? Bcrypt-hashed password login.
  2. Authorization — What are you allowed to do? Roles map to permissions; a single reusable decorator enforces every gated route the same way.
  3. Audit — What did you actually do? Every login attempt, permission check, and role change is written to an immutable log — success or failure.
Why This Project

I work as a Remittance Processing Clerk at JPMorgan Chase, auditing high-volume documents under compliance and security standards, and I'm studying Enterprise and Banking Systems at UT Dallas. This project was built to demonstrate — with real, running code — the access-control and auditability patterns that underpin enterprise IT and banking systems, rather than just describing them on a resume.

Architecture

Two containers — app (Flask) and db (Postgres 16) — defined entirely as code in docker-compose.yml. The whole stack comes up with one command: docker compose up -d --build. No local Python or Postgres install required.

Data Model
erDiagram
    USERS ||--o{ USER_ROLES : has
    ROLES ||--o{ USER_ROLES : "assigned to"
    ROLES ||--o{ ROLE_PERMISSIONS : grants
    PERMISSIONS ||--o{ ROLE_PERMISSIONS : "granted via"
    USERS ||--o{ AUDIT_LOG : "acts as"

    USERS {
        int id PK
        string username
        string password_hash
        bool is_active
    }
    ROLES {
        int id PK
        string name
    }
    PERMISSIONS {
        int id PK
        string name
    }
    USER_ROLES {
        int user_id FK
        int role_id FK
    }
    ROLE_PERMISSIONS {
        int role_id FK
        int permission_id FK
    }
    AUDIT_LOG {
        int id PK
        int user_id FK
        string username_attempted
        string action
        string resource
        bool success
        timestamptz created_at
    }

role_permissions and user_roles are pure many-to-many join tables with no surrogate key — the pair of foreign keys is the primary key, so the database itself refuses a duplicate grant instead of relying on application code to catch it. audit_log.user_id is nullable, paired with a separate username_attempted text column, so a failed login against a username that doesn't even exist is still captured with what was actually typed, instead of being dropped for failing a foreign key.

Role → Permission Matrix

Modeled on real separation-of-duties in banking — notably, the Auditor can view the audit trail but cannot edit accounts or approve transactions. An auditor who could act on what they're reviewing would defeat the point of having one.

Key Engineering Decisions
  • Enforcement lives in one place. A single require_permission(...) decorator gates every protected route by checking the logged-in user's permissions against the database. No route hand-rolls its own access check, so there's exactly one place to audit, test, or fix authorization logic.
  • The audit layer bolts on without touching auth logic. Audit logging was added in a later phase than login and permission checks, on purpose — it plugs into the existing decorator and login route as an addition, proving the three layers (authn/authz/audit) are genuinely decoupled, not just described that way.
  • UI never hides what the server will block. Every user sees every navigation link, regardless of role. Clicking one you're not permitted to use hits a real 403 from the server. This is a deliberate demonstration that access control has to be enforced server-side — hiding a button is not security.
  • Login errors don't leak information. A wrong password, a nonexistent username, and a disabled account all return the identical generic "Invalid username or password" message. Distinguishing between them would let an attacker enumerate which usernames are real.
  • Secrets never touch source control. Database credentials and the Flask session-signing key live in a git-ignored .env file; .env.example documents the required variables without real values.
  • Schema changes as live migrations, not resets. When a new permission (manage_roles) was needed after the database already had real audit data in it, it was added via a live SQL migration rather than wiping and reseeding — the same discipline a production system requires, since you don't get to just delete a live database's history.
Try It
Terminal
# clone and configure
git clone https://github.com/cadenjames667-ls/iam-rbac-demo
cd iam-rbac-demo
cp .env.example .env      # fill in your own DB credentials and Flask secret key

# build and seed
docker compose up -d --build
docker compose exec app python seed_users.py

Then open http://localhost:5000 and log in as any of the seeded demo accounts:
